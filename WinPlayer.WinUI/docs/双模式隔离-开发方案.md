## 1. 目标与非目标

### 1.1 目标

**普通模式与隐私模式在四层互不干扰**：

| 层 | 隔离内容 |
| --- | --- |
| 记录层 | 播放位置记录各写各的；隐私记录不可见（不泄漏到普通模式的列表显示与自动播放） |
| 状态层 | `settings.json` 双文件；`playlist.json` 隐私侧只读 |
| 进程层 | **各自独立的单例互斥体与激活管道**，两种模式可同时运行、互不激活 |
| 系统身份层 | **不同的任务栏图标 + 独立 AUMID**，任务栏可区分、跳转列表不共用 |

### 1.2 非目标（明确不做）

- 让隐私数据"不可读"：记录与设置仍是明文 JSON。**隔离 ≠ 加密**；要不可读需另立加密库需求。
- 资源管理器里 exe 文件图标区分：两模式共用同一 exe，需第二份 exe 或专用快捷方式才能做到。
- 隐私启动时联动暂停普通实例：不引入跨模式 IPC（避免新的耦合与可观测性）。
- 修改 `MyResourceManager`：它只需继续按清单下发 `--privacy` 参数。

## 2. 已定稿决策

| # | 决策 | 取值 | 理由 |
| --- | --- | --- | --- |
| D1 | 记录落盘形态 | **B′**：分区语义按 B（逻辑上两分区），物理上**两份文件** | 与"各自单例、两实例并发"天然兼容，无需跨进程合并协议；效果与 B 等价 |

### 2.1 被本方案删除的既有机制

删除 `SkipNextAutoResume` 一次性隐私标记及其全部配套（`MarkSkipNextAutoResume` / `ConsumeSkipNextAutoResume` / `oneShotPrivacyMarksConsumed` / `privacySkippedPaths` / `GetMostRecentPlayablePathAsync(excludedPaths)` / `Clear` 与 `ClearWithPrivacy` 的拆分）。

原因：隐私不再是"需要被消费的状态"，而是"数据存放位置"这一事实。自动播放只读普通区，因此隐私记录结构性不可能成为候选。当前实现中反复踩坑的三处（标记被播放结束清掉、隐私启动写空播放列表、标记消费时机）全部随之消失。

## 3. 架构

### 3.1 模式判定：纯函数、进程级、不可变

新增 `AppMode.cs`：

```csharp
internal static class AppMode
{
    private static readonly Lazy<bool> current = new(() => Detect(Environment.GetCommandLineArgs()));

    /// <summary>当前进程是否为隐私模式。由启动参数唯一决定，会话内不可变。</summary>
    public static bool IsPrivacy => current.Value;

    /// <summary>文件名后缀：普通为空，隐私为 ".b"。</summary>
    public static string Suffix => IsPrivacy ? ".b" : string.Empty;

    /// <summary>互斥体/管道名后缀：普通为空，隐私为 ".b"。</summary>
    public static string Tag => IsPrivacy ? ".b" : string.Empty;

    /// <summary>纯函数：参数中是否出现 --privacy / -privacy / /privacy / Privacy:（供单元断言）。</summary>
    public static bool Detect(IReadOnlyList<string> arguments);
}
```

**为什么必须是纯函数**：`AppLogService.LogPath` 是 `static readonly`（`Services\AppLogService.cs:20`），`SettingsService.path` 也在字段初始化时求值。模式若由"先构造服务、再设置状态"的可变量表达，必然出现初始化顺序陷阱。由 `argv` 推导则在任何时刻都正确；且**无参启动必然等于普通模式**，模式永远显式。

### 3.2 资源与文件布局

| 资源 | 普通模式 | 隐私模式 | 隐私侧行为 |
| --- | --- | --- | --- |
| 播放记录 | `playback-history.json` | `history.b.json` | 本区优先读、回退普通区；**只写本区** |
| 设置 | `settings.json` | `settings.b.json` | 首用由普通设置种子化（内存），首次 Save 落盘 |
| 日志 | `Logs\winplayer.log` | `Logs\winplayer.b.log` | 独立文件；默认不写完整路径 |
| 启动崩溃日志 | `startup-error.log` | `startup-error.b.log` | 独立 |
| 播放列表（含媒体文件夹列表） | `playlist.json` 读/写 | **只读**，退出不写回 | 顺带消除"NAS 离线导致列表被裁"的既有隐患 |
| 窗口/任务栏图标 | `Images\player.ico` | `Images\player.b.ico` | `AppWindow.SetIcon` |
| 任务栏 AUMID | `WinPlayer.WinUI` | `WinPlayer.WinUI.b` | 建窗**之前**调用 |
| 单例互斥体 | `Local\WinPlayer.WinUI.SingleInstance` | `…SingleInstance.b` | — |
| 激活命名管道 | `WinPlayer.WinUI.Activation` | `…Activation.b` | — |
| 文件关联注册表刷新 | 执行 | **跳过** | 不改注册表 |
| exe / 图标资源 / libmpv 运行库 | 共享只读 | 共享只读 | — |

目录（均为 `%LOCALAPPDATA%\WinPlayer.WinUI\`）：

```text
playback-history.json     普通记录
history.b.json            隐私记录
settings.json             普通设置
settings.b.json           隐私设置
playlist.json             播放列表（隐私模式只读）
startup-error.log / startup-error.b.log
Logs\winplayer.log / Logs\winplayer.b.log
```

### 3.3 进程与身份模型

| 启动情形 | 期望行为 |
| --- | --- |
| 普通启动，已有普通实例 | 转发参数并激活该窗口（现状） |
| 普通启动，**只有隐私实例** | **新开普通实例**，绝不激活隐私窗口 |
| 隐私启动，已有隐私实例 | 转发到隐私窗口（同模式，记录仍进隐私区） |
| 隐私启动，**只有普通实例** | **新开隐私实例**，绝不激活普通窗口 |
| `SingleInstance=false`（各模式读自己的设置） | 各自自由多开 |

两实例并存是设计结果：允许同时播放、互不联动。代价是可能出现双份解码与音频重叠，已在文档中明示，不做联动。

### 3.4 数据模型与读写语义（B′）

记录文档保持**单分区**结构（不需 `PrivateEntries`，因为隐私记录写另一个文件）：

```jsonc
{ "Version": 4, "Entries": { "<媒体完整路径>": { "Position": 0, "Duration": 0, "UpdatedUtc": "", "FileSize": 0, "FileLastWriteUtc": "", "FileName": "", "Fingerprint": "" } } }
```

| 场景 | 写 | 读 |
| --- | --- | --- |
| 隐私打开的文件 | 隐私文件 | 隐私文件优先，未命中回退普通文件 |
| 普通打开 | 普通文件 | 只读普通文件，**绝不读隐私文件** |
| 启动自动播放目标 | — | 只读普通文件 |
| 保留天数 / 条数上限 | 各自作用于自己的文件 | — |

迁移：v3 → v4 丢弃 `SkipNextAutoResume` 字段；`Entries` 原样保留。旧 `settings.json` 作为普通设置，隐私设置文件懒创建（**不从普通记录库复制**，避免隐私库一开始就是普通库的副本）。

## 6. 验证方案

### 6.1 测试脚手架改造（重要）

为 `PlaybackHistoryService` / `SettingsService` / `AppMode` 提供可选 `dataDirectory` 注入（仅测试用），使断言可在**临时目录**执行，不再触碰真实 `%LOCALAPPDATA%` 数据。此前为排障反复备份/还原用户数据的方式自此退役。

### 6.2 不变量清单

| # | 不变量 | 断言方式 |
| --- | --- | --- |
| I1 | 隐私启动完全不动普通记录 | `playback-history.json` SHA256 前后相等 |

## 7. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 双记录文件带来认知负担（"我上次看到哪了"） | 隐私进度只在隐私模式可见是设计本意；设置页提供"隐私记录"查看/清空 |
| 隐私设置种子化后长期分叉 | 设置页提供"从普通模式同步"一次性入口 |
| 两实例并存 → 双份解码、音频可能重叠 | 文档明示；不做联动（如需暂停联动另立需求） |
| 记录/设置仍为明文 | 文档明确"隔离 ≠ 加密" |
| 互斥体/管道名暴露"存在隐私实例" | 中性后缀 `.b`（D6） |
| 隐私实例读普通记录文件时的并发替换 | 保留"临时文件 + 原子替换"；读取侧对 `IOException` 重试 |
| 隐私会话内点击列表文件被误记为普通记录 | 按**会话模式**归属（I11）；设置页可清 |

**D. 说明与限制**

- `GetApplicationUserModelId` 对无包标识进程一律返回 `APPMODEL_ERROR_NO_APPLICATION`(15703)，因此 AUMID 只能以"应用内调用返回 S_OK + 日志值"作为证据；**任务栏是否为两个独立按钮需人工目视确认**（窗口图标差异已由图标句柄断言）。
- I6（并发无丢失）在 B′ 形态下由"两份文件 + 各自单例"结构性保证，并已由"普通记录逐字节未变"这一更强的断言实测覆盖。
- 隐私侧"回退续播"在端到端层面未被隔离证实（本机 `SkipIntroSeconds=133.5` 覆盖了续播起点），但已由临时目录单元断言证实（隐私模式读到普通记录 Position=100）。
- I11（隐私会话内点列表其他文件 → 记录进隐私区）由"整进程单一模式 + 单一服务实例"结构性保证，未做 UI 自动化测试。

### 9.2 实现期间发现并修复的问题

1. `MainWindow.xaml.cs` 中 `Path.GetFileName` 误用（该文件作用域的 `Path` 是 XAML 形状类型），导致 C# 编译失败并连锁引发 XAML 二次编译报错 → 改为 `System.IO.Path.GetFileName`。

3. `App.xaml.cs` 构造函数编辑时一度误删 `InitializeComponent()` 与三个未处理异常订阅，已在同轮发现并恢复（随后编译 0 警告 0 错误）。同时把 AUMID 设置的返回值写入启动日志（`AumidResult`），使任务栏身份可核查。

## 附录 B：启动参数契约

```text
WinPlayer.WinUI.exe --privacy "<文件>"     # 开关：本次命令中所有显式文件按隐私模式处理
WinPlayer.WinUI.exe "Privacy:<文件>"       # 前缀：仅该文件，且立即播放
WinPlayer.WinUI.exe "<文件>"               # 普通模式
WinPlayer.WinUI.exe "Play:<文件>"          # 立即播放（现有约定）
WinPlayer.WinUI.exe "Folder:<目录>"        # 目录参数（隐私模式下不改动列表）
WinPlayer.WinUI.exe "Records:<目录>"       # 兼容旧约定，WinUI 版忽略
```

语义：隐私模式 = "本次打开的文件不进播放列表、不写普通记录、不触发普通模式的自动播放；播放位置记入隐私记录，下次隐私打开可续播"。
